## Overview

Official public promotion of the `3.18.x` cycle succeeding stable release [3.17.2](2026-11-02_3.17.2.md) on `zcode.z.ai/changelog` (carrying 56 cumulative official release-note items = 42 from preview [3.18.0](2026-11-10_3.18.0.md) + 10 from preview [3.18.1](2026-11-11_3.18.1.md) + 4 net-new `3.18.2` fixes). Static binary diff against preview `3.18.1` (~21.5 hours after `3.18.1-10376`) confirms a targeted credential, authentication, and updater hotfix: on Linux `x86_64`, the Electron runtime and all unpacked native addons are bit-for-bit unchanged; all application-layer changes concentrate in `app.asar` (`+12,780` B) and `glm/zcode.cjs` (`+2,722` B) across three credential/account mechanisms—post-migration OS keyring key sharing, Linux Secret Service private-file key fallback, and standalone Start Plan material resolution with `zai_cn` → `bigmodel` family mapping—alongside a Windows updater path/restriction fix.

## Credential, Account & Updater Fixes

- **Post-Migration Credential Key Sharing (`credential-key-share` IPC)**
  - `updateDataBaseDir` now invokes `shareCredentialKeyWithDataRoot` immediately after copying the data directory, sending a strict Zod-validated `credential-key-share-request` (`{ type, requestId: uuid, targetBaseDir: string(1..32767) }`) over the host-to-main worker port.
  - Main-process `spawnHostProcess` (`out/main/index.js`) verifies `targetBaseDir` is absolute (rejecting with `"Data root must be absolute"` otherwise) and executes `shareKeyWithCopiedCredentials` against `<newRoot>/.zcode/v2/credentials.json`: compares embedded 24-hex OS keyring key fingerprints (`enc:v2:os:<24hex>:`) across source and target via `keyFingerprint` / `encodedKeyFingerprint` / `readOsKeyFingerprints` and checks `isOsSourcePinned` (`credential-source` == `"os\n"`), then writes the source OS keyring key in `base64url` to `<newRoot>/.zcode/v2/credentials.json.keyring` so copied credentials remain decryptable without creating a new OS keyring item.
  - Replies with `credential-key-share-result` (`ok` or `errorCode: "CREDENTIAL_SECURE_STORAGE_UNAVAILABLE"`) and logs `[credential-key-share] completed|failed`. Registered across 7 of 8 preload bundles (`out/preload/{index,codingPlanWebview,cuaPermissionPanel,embeddedBrowserJavaScriptDialog,pluginSandbox,resourceManager,rewardsWebview}.cjs`), `out/scheduler/index.js`, main/host shared message chunks (`chunk-N4BDK3A6.js` / `chunk-IEBWXNOE.js`), and CLI runtime exports (`hostCredentialKeyShareRequestResponseSchema` / `hostCredentialKeyShareResultMessageSchema`).
- **Linux Secret Service Private-File Key Fallback (`enablePrivateFileKeyFallback`)**
  - `createSystemCredentialCipher`'s `getKey` failure path now catches OS keyring set/get verification errors and—when `credential-source` is not pinned to `os`/`env` and the fallback hook is armed—calls `publishPrivateSecretFile` to generate a 32-byte random `base64url` secret written exclusively (`mode: 0o600` / `384`, `flag: "wx"`) to `<dataRoot>/.zcode/v2/credential-secret.<pid>.<hex>.tmp` and atomically renamed to `credential-secret` (tolerating `EEXIST`), then resolves the managed secret (`source: "env"`) and invokes `onFallback`.
  - **Three-copy bundle wiring**: Wired and active in the Electron **main process** (`out/main/index.js` calls `enablePrivateFileKeyFallback` on `process.platform === "linux"` against `out/main/chunk-5SVAX2QO.js`, logging `[credential] Linux 系统凭据库不可用，已改用私有文件密钥` on fallback, or refusing registration with a warning if credentials were already accessed while `Zd.size > 0`); present in source-synced copies inside **host** (`out/host/index.js`) and **CLI** (`glm/zcode.cjs`) bundles with 0 hook assignments (statically unreachable there).
- **Decoupled Start Plan Material & `zai_cn` → `bigmodel` Mapping**
  - Host process (`out/host/index.js`, `+3,862` B) introduces `loadStartPlanMaterial` and `startPlanMaterialFromSnapshot`, returning `{ family, loginProvider, zcodeUserId, sessionRevision, accountIdentity, zcodeJwtToken }` **without** requiring a full OAuth `accessToken`, and switches `start-plan` API key derivation from `loadOAuthTokenSet(family)` to `loadStartPlanZcodeJwt(family)`.
  - `createCodingPlanFamilyAvailabilityResolver` now validates scope consistency across both `accountMaterial` and `startPlanMaterial` (`project_token_scope_invalidated`), `resolveStartPlanAuthorization` reads `startPlanMaterial?.zcodeJwtToken`, and `resolveCurrentAccountAccess` uses `isStartPlanFamilyCurrent` + per-plan `identityOf("start-plan")` so missing family-level `individual-coding-plan` identity no longer marks Start Plan `unavailable (coding_plan_not_connected)`.
  - Added `resolveStartPlanFamilyFromOAuthProvider` (`out/host/chunk-IEBWXNOE.js` and exported in `glm/zcode.cjs`), explicitly mapping `zai_cn` to the `"bigmodel"` Start Plan family alongside `resolveProviderFamilyDomainFromOAuthProvider`.
- **Windows Updater Fix (Official Release Notes)**
  - Fixed checking for updates failing on Windows under system restrictions or when installation/profile paths contain special characters.
